# Задача 16 (ver3, minimax) — ReactTest: фиксация императивной логики навбара тестами

Версия v3 развивает решения v1/v2 (см. §0.5 «Отличия»): стратегия **A+E** —
**основная ветка** (чистые политики в `machine/navPolicy.ts`, подход из v2,
D1) **плюс расширенная граница покрытия**: покрыть не только политики, но и
тонкие обвязки хуков (`useNavPosition`, `useToggleVisibility`, `useLayoutApplier`)
через **поведенческие моки GSAP + jsdom** (подход E, новый для v3). Подход C
(`renderHook` + `@testing-library/react`) — отложен до явной потребности
(D8 v2 сохранён).

### 0.5 Отличия от v2 (для чистого сеанса)

- **Стратегия объединена в A+E:** v2 имел один подход (A — чистые политики).
  v3 идёт дальше: A (already-done в v2 базово, но расширено) + E (новый —
  поведенческие моки хуков на jsdom без `@testing-library/react`).
- **Mock-стратегия — `vi.mock('gsap')` через `setupFiles`** (D2 v3):
  единая фабрика fake-tween покрывает `to`/`fromTo`/`ticker`/возвращаемый
  тип. `useGSAP` из `@gsap/react` мокается на no-op-обёртку, которая
  вызывает колбэк с `(root, ctxSafe)`, где `ctxSafe` пробрасывает
  пользовательские функции напрямую (тесты проверяют **что хук передал**
  в `gsap.to`, а не рендерят React).
- **`@testing-library/react` НЕ используется** (D3 v3): вместо него —
  прямой вызов экспортируемых чистых функций + тонкие `act` из `react`.
  Это сохраняет политику «минимум devDeps» из D1 v2.
- **Render-вспомогатель `renderHookLite`:** собственная утилита в
  `src/test/renderHookLite.tsx`, использующая `createRoot` из `react-dom/client`
  (входит в React 19) + `act` из `react`. Никаких новых рантайм-зависимостей.
- **Базлайн v2 (задача 16 v1/v2 фазы 1–4) считается выполненным**: файл
  `machine/navPolicy.test.ts` уже есть. Эта задача **поверх него** —
  добавляет E-фазу. Если v2-фазы ещё не завершены — сначала закрыть их (см. §3.0
  «Входной гейт»).
- **`It.each` table-driven** сохранён из v2 (D6 v2), GWT-имена — из
  `testing.md`. Для хуковых тестов добавлен формат **«Arrange → act → assert»
  с явными секциями**, т.к. fixture крупнее.
- **`ScrollTrigger` мок:** `vi.mock('gsap/ScrollTrigger', () => ({ refresh: vi.fn(), create: vi.fn() }))`
  — минимальный набор для `useLayoutApplier`.
- **`EDGE_EPS` остаётся в `GsapProvider.tsx`**, хуки импортируют его
  напрямую — тесты мокают модуль `GsapProvider` при необходимости
  подменить значение (D4 v2 сохранён: политика чистая принимает параметром;
  E-тесты тестируют обвязку хука целиком с реальным `EDGE_EPS`).

### 1.3 Почему это надо фиксировать (расширение v2-блока)

1. Политики без обвязки — половина покрытия: можно отрефакторить хук «правильно»
   по политике, но перепутать порядок `kill → fromTo → progress` и получить
   кадровый глитч (это **уже** было, см. `useNavPosition.ts:47-49`).
2. `prevManualRef.current = manualNow` **обязан** идти **после** skip-guard —
   иначе skip-логика сломается (см. комментарий в v2 §3 F2).
3. Resync guard — `if (!isHome || isManualToggle) return;` стоит **до** invalidate
   и подписки; тест фиксирует «подписки нет, инвалидации нет» в обеих ветках.

interface FakeTween {
  fromVars?: Record<string, unknown>;
  toVars: Record<string, unknown>;
  killed: boolean;
  _progress: number;
  pause(): this;
  resume(): this;
  kill(): this;
  progress(value?: number): number;
  invalidate(): this;
}

function createFakeTween(
  fromVars: Record<string, unknown> | undefined,
  toVars: Record<string, unknown>,
): FakeTween {
  const t: FakeTween = {
    fromVars,
    toVars,
    killed: false,
    _progress: 0,
    pause() {
      return this;
    },
    resume() {
      return this;
    },
    kill() {
      this.killed = true;
      return this;

    progress(value?: number) {
      if (typeof value === 'number') this._progress = value;
      return this._progress;
    },
    invalidate() {
      return this;
    },
  };
  return t;

  target: unknown;
  vars: Record<string, unknown>;

## 6. Риски и принятые решения

- **R1 — `renderHookLite` велосипед вместо `@testing-library/react`.**
  Митигация: 0 devDeps; код ~30 строк; повод использовать — D8 v3
  (минимум зависимостей). Если в будущем понадобится рендеринг JSX —
  отдельная задача введёт RTL.
- **R2 — `useGSAP` мок не синхронен с реальным `gsap.context()`.**
  Реальный `useGSAP` на mount вызывает колбэк **синхронно** внутри
  `useLayoutEffect` (см. `@gsap/react` API). Мок воспроизводит это.
  `contextSafe` — реально просто обёртка `() => fn.apply(this, arguments)`
  внутри gsap.context; для тестов pass-through достаточен. Разница может
  проявиться, если хук начнёт использовать `ctx.add(() => ...)` —
  v3 отлавливает это в tripwire.
- **R3 — `setupFiles` мок может зацепить чистые тесты в node.**
  `vi.mock` работает в обоих окружениях; mock GSAP возвращает fake-tween
  при `fromTo`/`to` — чистые `transition.test.ts`/`geometry.test.ts`/`engine.test.ts`
  НЕ импортируют gsap, поэтому не задеты. Проверка в Фазе 1.
- **R4 — `window.innerWidth` мок.**
  По умолчанию 1024 в setupFiles. Если тест хочет другое — использует
  `Object.defineProperty(window, 'innerWidth', { value: 800 })` в Arrange
  (восстанавливается в afterEach).
- **R5 — тройное повторение setup-обвязки** в каждом test-файле (engine +
  GsapContext.Provider + RegisterSpacerScrollTriggerContext.Provider).
  Митигация: helper `makeRenderEnv(bp, isHome, ...)` в каждом тестовом
  файле (~15 строк) или — единый `src/test/renderEngine.tsx` если
  дублирование станет заметно после первой итерации.
- **R6 — `vitest.config.ts` vs `vite.config.ts`.**
  Vite 8 поддерживает блок `test:` в `vite.config.ts`. Если ESLint/typescript
  ругается на `test:` в vite-config — вынести в `vitest.config.ts` отдельно.
