# NavScrub: синхронизация границы навбар/контент (последствия задач 16/17)

## Контекст (общий)

Задачи `16.FullLayoutRefactoring` и `17.SyncNavRetargetScrub` довели
синхронность анимации навбара и контента: дискретный твин навбара теперь
читает `snapshot.transition`, а перецеливка scrub-а на `/home` при TOGGLE
плавно анимируется синхронно с контентом. Однако при решении вскрылись две
смежные недоработки, бьющие в одну зону — `useNavPosition.ts`
(пересборка/перецеливка scrub-твина через `scrubTweenRef` и `buildScrub`).

Обе подзадачи ниже изолированы по триггеру, но правят один модуль, поэтому
берутся одной сессией/коммитом. Точка пересечения и нужный порядок — в
разделе «Порядок реализации».

---

## Подзадача 1 — RC2: ресайз внутри breakpoint

### 📋 Описание

**Проблема:** На `/home` после прокрутки spacer-а изменение ширины окна
**внутри одного breakpoint** (tablet 800→980, desktop 1200→1400, mobile,
смена ориентации без пересечения границы) рассинхронизирует границу:
контент адаптируется мгновенно (CSS-переменная `25vw`/`80px`), а навбар
«плывёт».

**Симптомы:**

- Контент занимает корректную ширину/offset.
- Навбар стоит на устаревшей позиции (scrub-твин «запечён» со старой ширины
  вьюпорта) → видимая щель или перекрытие.

**Важно:** пересечение границы breakpoint (`tablet ↔ desktop` и т.п.) — **не**
часть этой подзадачи. При `BREAKPOINT_CHANGED` меняется `bp`, который входит
в зависимости `useGSAP`, поэтому scrub пересобирается корректно. Здесь
только **внутри-breakpoint** ресайз.

### 🔍 Анализ

`buildScrub` (`src/components/Layout/nav/NavigationBar/useNavPosition.ts`)
читает `window.innerWidth` один раз при сборке и строит
`fromTo(nav, {x:0} → {x: getNavTransform(homeEndState, window.innerWidth).navX},
ease:'none', paused:true)`. Зависимости `useGSAP` —
`[navRef, engine, snapshot.homeEndState, snapshot.bp, snapshot.isHome]` —
**не содержат viewport**. При ресайзе внутри breakpoint `buildScrub` не
перезапускается, `endX` остаётся под старую ширину.

Проявляется только при `progress > 0` scrub-а (spacer промотан), т.к. на
верху (`progress 0`) навбар всегда в `x:0` независимо от `endX`.

### 🎯 Цели

1. При ресайзе внутри breakpoint на `/home` покойная позиция навбара
   совпадает с контентом (без анимации, snap — как у контента).
2. Не сломать пересечение breakpoint и скролл после ресайза.

### 🛠️ План

В `useNavPosition.ts` внутри `useGSAP` добавить `window.resize`-слушатель
(снять в cleanup), который при `snapshot.isHome` **мгновенно** пересобирает
scrub-твин:

```ts
function handleResize() {
  if (!snapshot.isHome) return;
  const progress =
    scrubTweenRef.current?.progress() ?? getSpacerScrollProgress();
  scrubTweenRef.current?.kill();
  scrubTweenRef.current = gsap.fromTo(
    nav,
    { x: 0 },
    {
      x: getNavTransform(snapshot.homeEndState, window.innerWidth).navX,
      ease: 'none',
      paused: true,
      immediateRender: false,
    },
  );
  scrubTweenRef.current.progress(progress);
}
window.addEventListener('resize', handleResize);
// cleanup: window.removeEventListener('resize', handleResize)
```

Отдельный путь от анимированной перецеливки (toggle): ресайз должен
**snap**-ать, как контент, без `0.45s`-твина.

### Тесты

`useNavPosition.test.tsx` — меняем `window.innerWidth`, эмитим
`scroll:progress`, проверяем, что `endX` scrub-твина обновился под новый
viewport, а прогресс сохранён.

### Критерии приёмки

- Ресайз внутри breakpoint на `/home` (после прокрутки) → граница
  навбар/контент совпадает мгновенно.
- Пересечение breakpoint не сломано.
- Скролл после ресайза ведёт навбар корректно.

## Подзадача 2 — RETARGET_SCRUB: явная обработка (вариант A)

### 📋 Описание

**Проблема:** `docs/Components/Layout/README.md` утверждает, что
`GsapProvider` исполняет `SCROLL_TO_END` **и** `RETARGET_SCRUB`. Фактически
`GsapProvider.subscribeActions` обрабатывает только `SCROLL_TO_END`;
`RETARGET_SCRUB` **нигде не потребляется**.

Перецеливка scrub-а сейчас работает **побочно**: при TOGGLE на tablet
меняется `homeEndState`, входящий в зависимости `useGSAP`, что
перезапускает `buildScrub`, а тот проигрывает анимированную перецеливку
(добавлено в задаче `17`). Связь хрупкая: держится на наличии
`homeEndState` в deps.

**Цель (вариант A):** сделать обработку `RETARGET_SCRUB` явной — навбар
подписывается на `engine.subscribeActions` и при `RETARGET_SCRUB` сам
запускает анимированную перецеливку. Приближает к документированному
контракту и убирает скрытую зависимость.

### 🔍 Текущее состояние

- `engine.ts`/`transition.ts`: `RETARGET_SCRUB` эмитится при TOGGLE на tablet
  (`standard ↔ slim`).
- `GsapProvider.tsx`: `subscribeActions` реагирует только на `SCROLL_TO_END`.
- `useNavPosition.ts`: анимированная перецеливка — ветка `hadScrub` внутри
  `buildScrub` (`gsap.to(nav, {x: endX*prevProgress, duration:
snapshot.transition.duration, ease: snapshot.transition.ease, onComplete →
пересборка scrub})`).

### 🎯 Цели

1. `RETARGET_SCRUB` обрабатывается явно в `useNavPosition`, не побочно.
2. Поведение перецеливки не меняется (та же плавная анимация, синхронная с
   контентом).
3. Не сломать текущую синхронизацию.

### 🛠️ План

**Этап 1 — вынести перецеливку в именованную функцию.** Извлечь логику
ветки `hadScrub` в `retargetScrub()`:

```ts
const retargetScrub = contextSafe!(() => {
  const progress =
    scrubTweenRef.current?.progress() ?? getSpacerScrollProgress();
  const endX = getNavTransform(snapshot.homeEndState, window.innerWidth).navX;
  scrubTweenRef.current?.kill();
  scrubTweenRef.current = null;
  gsap.to(nav, {
    x: endX * progress,
    duration: snapshot.transition.duration,
    ease: snapshot.transition.ease,
    overwrite: 'auto',
    onComplete: () => {
      scrubTweenRef.current = gsap.fromTo(
        nav,
        { x: 0 },
        { x: endX, ease: 'none', paused: true, immediateRender: false },
      );
      scrubTweenRef.current.progress(getSpacerScrollProgress());
    },
  });
});
```

**Этап 2 — подписка на действие.** В `useNavPosition.ts` добавить
подписку (очистка в cleanup `useGSAP`):

```ts
const unsubscribeActions = engine.subscribeActions((actions) => {
  for (const action of actions) {
    if (action.type === 'RETARGET_SCRUB' && scrubTweenRef.current) {
      retargetScrub();
    }
  }
});
```

`scrubTweenRef.current` как guard: перецеливка имеет смысл только когда
scrub уже построен (на `/home`).

**Этап 3 (опционально, отдельным коммитом).** После проверки Этапов 1-2
рассмотреть вынос `snapshot.homeEndState` из зависимостей `useGSAP`
(оставить `isHome`/`bp`), чтобы сборка шла по факту `/home`, а перецеливка —
по действию. **Риск:** `homeEndState` пересчитывается в `engine.send` и по
другим событиям; перед удалением из deps убедиться, что `RETARGET_SCRUB`
покрывает все нужные случаи.

### Тесты

`useNavPosition.test.tsx` — при TOGGLE на `/home` навбар анимируется
(`gsap.to` с `duration/ease === snapshot.transition`), перецеливка
запускается по `RETARGET_SCRUB`.

### Критерии приёмки

- `RETARGET_SCRUB` обрабатывается явно, перецеливка синхронна с контентом.
- Поведение визуально не меняется.
- Тесты и сборка зелёные.

## Порядок реализации и пересечения

- Обе подзадачи правят `src/components/Layout/nav/NavigationBar/useNavPosition.ts`
  и `useNavPosition.test.tsx` → делать **одной сессией/коммитом**.
- Подзадача 2 меняет _механизм_ перецеливки (`retargetScrub` + подписка на
  действие); Подзадача 1 добавляет _resize-листенер_ с мгновенной
  пересборкой. Разные триггеры: resize = snap, действие = анимация — они не
  должны конфликтовать, но при реализации проверить, что resize-листенер не
  срабатывает во время проигрывания `retargetScrub` (навбар уже на цели).
- Файлы: `useNavPosition.ts`, `useNavPosition.test.tsx`.
- Общая верификация: `npm run test` / `npm run lint` / `npm run build` +
  ручная `/home` tablet: TOGGLE (синхронно), ресайз внутри breakpoint
  (совпадает мгновенно), пересечение breakpoint (работает), скролл после
  ресайза (ведёт корректно).

> Примечание: задача `RC3` (холостой content-твин на границах `REACH_*`) не
> трогается — безвредна и не ломает визуал.
