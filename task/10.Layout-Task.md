# Layout — техническое задание на рефакторинг

Техническое задание на итерацию рефакторинга модуля навигации (`NavigationBar`)
в layout-модуль. Цель — устранить противоречие между фактическим поведением
(контроль раскладки всей страницы) и самоописанием (диспетчер сцен с шиной
событий), и переписать под модель **layout-машина состояния + per-component
animator**.

---

## 1. Контекст и мотивация

### 1.1 Фактическое состояние

- `NavigationBarProvider` оборачивает весь `App` и рендерит корневую колонку:
  навбар `fixed` + контентную область `<main>{children}</main>` с отступом
  `--nav-content-offset`.
- Контентный лейаут (`margin-left`/`width` `<main>`) — прямое следствие состояния
  навбара (`getContentOffset`).
- На `/home` ScrollTrigger на контентном спейсере ведёт ширину навбара (scrub,
  60fps), а на mobile ручной toggle программно прокручивает `window`.

То есть компонент — фактически **движок раскладки всей страницы**, а не
«презентационная панель».

### 1.2 Ключевое противоречие

Модуль построен как «диспетчер сцен с типизированной шиной событий»
(`NavbarEventBus`, `bus.emit('state:change')`, `useNavbarEvent`, каналы). Это
плохо сочетается с задачей:

1. **Состояние живёт в машине, а переходы вычисляются извне машины** — на
   `bus.on('route:change'/'breakpoint:change'/'toggle:request')`. Центр машины
   «разобран» по подпискам.
2. **Непрерывный 60fps-скролл не ложится на дискретные события** — прогресс
   уже вынесен в отдельный низкоуровневый канал `onScrollProgress` (не шину),
   подтверждая, что шина для этого не подходит.
3. **Шина поощряет множество владельцев `.nav`** — требует single-owner трюков
   (`useNavbarPosition`, paused scrub + `overwrite`, mobile-пин), чтобы гасить
   гонку. Шина создала проблему, single-owner её лечит.

### 1.3 Мера простоты (ориентир)

Из ~1200 строк модуля убрать ~250–350 (слой «опосредования»: шина, подписки,
эмиссии) и радикально снизить связность между файлами. Остальная сложность —
не «шина», а суть задачи (scrub-панель по скроллу) и не должна исчезнуть.

## 2. Целевая архитектура

**Принцип:** один источник состояния (`LayoutMode` в React Context) + каждый
компонент сам строит свой GSAP-timeline из него. Никакой pub/sub/медиатора/
центрального аниматора.

```
LayoutProvider (useState<LayoutMode>; триггер-эффекты; низкоуровневые каналы)
   ├─ mode ───────── derive ── mainOffset / hasToggle / isSlim
   ├─ NavigationBar (панель): useLayout()
   │    ├─ NavPanel-position: единственный владелец .nav (scrub + discrete)
   │    │    └─ один низкоуровневый канал onNavState(prev,next,source) для .nav
   │    ├─ NavList/NavItem: useLayout() → собственный useGSAP(deps:[mode])
   │    └─ ToggleButton: клик → layout.toggle()
   ├─ <main>: offset = deriveMainOffset(mode)   (--nav-content-offset, как сейчас)
   └─ onScrollProgress / onToggleVisibility — низкоуровневые каналы (не трогаем)
```

### 2.1 Переименования

| Было                                  | Стало                                 |
| ------------------------------------- | ------------------------------------- |
| `NavigationBarProvider`               | `LayoutProvider`                      |
| Хук `useNavbar()`                     | `useLayout()`                         |
| `NavState`                            | `LayoutMode`                          |
| `NavbarSource`                        | `LayoutChangeSource` (сужен, см. п.5) |
| Папка `src/components/NavigationBar/` | `src/components/layout/`              |

Наименование «навигационная панель» остаётся за компонентом `NavigationBar` —
это часть layout, а не сам layout.

## 4. Правила развязки (кто что знает)

Однонаправленные зависимости: `nav → context → scenes → machine`; провайдер —
наверху.

- **`machine/`** — pure, без React и GSAP. Только типы и хелперы. Импортирует любой слой.
- **`scenes/`** — импортируют `machine` + контекст; **не** импортируют панели `nav/`.
  Каждая сцена владеет своей областью (state / toggle / scroll / позиция `.nav`).
- **`nav/`** — читают из контекста `mode`/`isSlim` (или получают пропом), строят свои `useGSAP`; не импортируют `scenes/` и провайдер.
- **`LayoutProvider`** — единственный, кто знает обе стороны: собирает сцены, держит низкоуровневые каналы, рендерит `nav` + `<main>`.

## 5. Удаляется (всё неиспользуемое «на перспективу»)

В рамках рефакторинга методы удаляются полностью. Если позже понадобятся —
паттерн восстановления описан в разделе 5.1.

| Что                                                                                  | Причина                                                       |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| `core/navbarEventBus.ts`, `NavbarEventMap`, `createNavbarEventBus`, `useNavbarEvent` | слой pub/sub убирается                                        |
| `spacer:enter` / `spacer:leave` (эмиссия в scrub-trigger)                            | **нет потребителей** (только задокументированы)               |
| `'intro'` в источнике изменения                                                      | мёртвый reserved, интеграция с IntroAnimation не спланирована |
| `events`/`bus` в публичном API, экспорты шины из `index.ts`                          | механика шины                                                 |
| `getContentOffset` → дублируется в `deriveMainOffset(mode)`                          | свернуть с `navState`; переиспользовать отступ напрямую       |

### 5.1 Как вернуть (заметка для будущих сессий)

- **`spacer:enter/leave`**: одна дискретная подписка на «спейсер снова вьюпорт /
  ушёл за экран». Если понадобится — добавить низкоуровневый Set-canal (по
  образцу `onScrollProgress`), emitter в `useScrollSpace.onUpdate`.
- **`'intro'`/интеграция с IntroAnimation**: `LayoutChangeSource` расширить на
  `'intro'`, при завершении intro вызвать `applyState(..., 'intro')` — контракт
  должен остаться совместимым с вариантом «один источник + per-component».

## 6. Публичный API модуля (`index.ts`)

Экспортируются только:

- компонент `LayoutProvider`
- хук `useLayout()`
- хелперы геометрии: `getNavTransform`, `SLIM_WIDTH`
- типы: `LayoutMode`, `LayoutChangeSource`, `NavTransform`

Экспортов шины событий больше нет.

## 7. Сохраняется без изменения поведения

Критично не скатить регресс:

- Скруб `/home` (60fps-канал `onScrollProgress`) — как есть.
- Видимость toggle (`onToggleVisibility`) — как есть.
- `--content-offset` для `<main>` (статичный offset, без reflow-скруба) — как есть.
- transform-навбар (`100vw` + `translateX`, не `width`) — как есть.
- Приоритет автоскролл > ручной; single-owner `.nav`; mobile-пин; `preferredRef`/
  `getHomeEndState`/`retargetScrub` — сохранить.
- Контракт страницы `registerScrollTrigger(trigger)` (`HomePage`) — без изменений.
- Персистентность ручного tablet-выбора между роутами — сохранить.

## 8. План исполнения (по фазам)

### Фаза 1 — `machine/` (чистая логика, без зависимостей)

1. `layoutMode.ts`: перенести `LayoutMode` (`fullscreen|standard|slim|invisible`)
   и `LayoutChangeSource` (`toggle|route|breakpoint|scroll`). Убрать `'intro'`.
2. `geometry.ts`: `SLIM_WIDTH`, `getNavTransform`, `getContentOffset` (из
   `navbarStates`), переименовать в `deriveMainOffset` при необходимости.
3. `derive.ts`: `getDefaultState`, `getNextState`, `homeEndStateFor`,
   `isPreferredStateValid`, `hasToggleFor`, `isManualMobileState`, `isHomePath`.

Допишить чистым: не импортирует React/GSAP/Context.

### Фаза 2 — `LayoutProvider/LayoutContext.ts` + `useLayout()`

- `LayoutContextValue = { mode, isSlim, hasToggle, toggle, registerScrollTrigger,
onScrollProgress, onToggleVisibility, onNavState, getHomeEndState,
registerRetargetScrub }`.
- `useLayout()` — бросает, если вне провайдера.

### Фаза 3 — `scenes/*`

- `useLayoutState`: состояние в `useState`, `applyState(next, source)` (одна
  точка записи), `preferredRef`, `getHomeEndState`. Убрать React-bridge на
  `bus.on('state:change')` (состояние итак в useState): напрямую `setMode`.
- `useLayoutToggle`: `toggle()` — handler, нет подписки `bus.on('toggle:request')`.
- `useScrollScrub`: `registerScrollTrigger(trigger)` — ScrollTrigger / границы /
  60fps-каналь `onScrollProgress` / `onToggleVisibility`. Убрать `spacer:*` и
  `bus.*`. Поле `scrollTriggerRef` (для auto-скролла на mobile /home).
- `useNavPosition`: единственный владелец `.nav`; подписка на `onNavState`
  (prev/next/source); paused scrub + discrete с `source !== 'scroll'`; retarget по
  `registerRetargetScrub`.

### Фаза 4 — `nav/*` (per-component animator)

- `NavItem`: заменить `useNavbarEvent('state:change')` демо-подписку на
  `useEffect([isSlim])` + prevRef (entered-slim) + `useGSAP`.
- `ToggleButton`: `onClick → useLayout().toggle()` (вместо `events.emit`).
- `NavigationBar`, `NavList`, `navItems`: читают `mode`/`isSlim` из контекста.
- Логотип/badge → паттерн «читает context + свой `useGSAP`» (рамка для будущих).

### Фаза 5 — `LayoutProvider.tsx`

- Машина состояния + триггер-эффекты (`useEffect([pathname, bp])` → recompute).
- Композер сцен (state, toggle, scrub) без шины.
- Каналы: `onScrollProgress`, `onToggleVisibility`, `onNavState`.
- Разметка: `<nav>` + `<main>` с `--nav-content-offset`.

### Фаза 6 — сборка/экспорты + внешние правки

- `index.ts` публичного API.
- Удалить старые файлы `src/components/NavigationBar/`.
- Обновить `App.tsx` (импорт `LayoutProvider`) и `HomePage.tsx` (`useLayout()`).

### Фаза 7 — доки
