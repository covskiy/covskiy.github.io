# Задача 16 — ReactTest: фиксация GSAP-логики навбара тестами

Навбар «накручивается»: в `useNavPosition.ts` и `useToggleVisibility.ts` растёт
оркестрация GSAP — решения «кто владеет позицией», условия skip, сохранение
прогресса, перерасчёт `endX` от `homeEndState` и `window.innerWidth`. Чистый
слой (машина + движок) уже покрыт (задача 13), а эти **политики решений** —
нет: они вшиты в React-хуки и не проверяются ни одним тестом.

Задача: вынести политики в чистые функции и зафиксировать их юнит-тестами
(подход A). Численные тесты scrub-маппинга на реальном GSAP (подход B) —
опциональная фаза 5. `renderHook` (подход C) — осознанно отложен (см. D8).

## 1. Анализ текущего состояния

### Инвентарь непокрытой логики

| #   | Кусок логики                                                         | Где живёт                      | Что решает / считает                                                                                                                  |
| --- | -------------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | **buildScrub** — строить ли scrub-твин, `endX`, сохранение прогресса | `useNavPosition.ts:43-78`      | `isHome` → нет: убить твин; да: `endX = getNavTransform(homeEndState, innerWidth).navX`, прогресс старого твина переживает пересборку |
| P2  | **Discrete skip** — владение x на `/home`                            | `useNavPosition.ts:82-112`     | `isHome && !manualNow && !prevManual` → пропустить `gsap.to` (scrub владеет x)                                                        |
| P3  | **Resync guard** — пересинхрон с спейсером + подписка на bus         | `useNavPosition.ts:132-142`    | `!isHome \|\| isManualToggle` → не пересинхронизировать и не подписываться                                                            |
| P4  | **Видимость toggle**                                                 | `useToggleVisibility.ts:46-51` | `hidden = !(progress >= 1 - EDGE_EPS \|\| isManualToggle)`                                                                            |

### Почему это надо фиксировать

1. Правки в «кто владеет x» и skip-условиях ломают поведение **без единого
   красного теста** — регрессии уезжают в проде.
2. `endX` связывает `homeEndState` (машина) и `window.innerWidth` (браузер) —
   перерасчёт легко сломать при рефакторинге машины.
3. `buildScrub` пересобирает твин **с сохранением прогресса** — тонкая логика,
   которая уже порождала кадровые глитчи (см. комментарий на стр. 45-48).

### Принцип разделения

Всё, что в этих местах является **решением или вычислением** — выносится в
чистые функции. В хуках остаётся только **обвязка** (refs, `useGSAP`,
подписки, вызовы `gsap.fromTo`/`gsap.to`). Это ровно тот паттерн, на котором
уже построен движок (`engine.ts` — тонкий оркестратор над чистой `transition`).

## 3. Извлекаемые политики (детально)

### F1. `decideScrubBuild` — решение buildScrub (P1)

```ts
export interface ScrubBuildDecision {
  /** true — строить/пересобрать scrub-твин; false — убить существующий. */
  shouldBuild: boolean;
  /** Конечный x навбара на /home; null, когда shouldBuild=false. */
  endX: number | null;
  /** Прогресс, который надо сохранить при пересборке. */
  prevProgress: number;
}

export function decideScrubBuild(opts: {
  isHome: boolean;
  homeEndState: LayoutMode;
  viewport: number;
  existingProgress: number;
}): ScrubBuildDecision;
```

Семантика (эквивалент `useNavPosition.ts:43-78`):

- `!isHome` → `{ shouldBuild: false, endX: null, prevProgress: 0 }` (хук киляет твин);
- `isHome` → `{ shouldBuild: true, endX: getNavTransform(homeEndState, viewport).navX, prevProgress: existingProgress }`.

Композиция чистая: `getNavTransform` уже из `machine/geometry.ts`. `viewport`
хук подставляет из `window.innerWidth`, `existingProgress` — из
`scrubTweenRef.current?.progress() ?? 0`.

### F2. `shouldAnimateDiscrete` — skip-решение (P2)

```ts
export function shouldAnimateDiscrete(opts: {
  isHome: boolean;
  manualNow: boolean;
  prevManual: boolean;
}): boolean;
```

Семантика: `!(isHome && !manualNow && !prevManual)` — анимировать дискретно,
**кроме** «/home без ручного управления и без ручного в прошлом» (там x держит
scrub). Важно: `prevManualRef` в хуке обновляется **только** при не-skip-ветке
(`useNavPosition.ts:96`), поэтому `prevManual` передаётся как вход, а не
вычисляется внутри.

### F3. `shouldResyncScrub` — guard useEffect (P3)

```ts
export function shouldResyncScrub(opts: {
  isHome: boolean;
  isManualToggle: boolean;
}): boolean;
```

Семантика: `isHome && !isManualToggle`. При `false` хук выходит из эффекта до
`invalidate()`/подписки на bus (`useNavPosition.ts:133`).

### F4. `shouldHideToggle` — видимость кнопки (P4)

```ts
export function shouldHideToggle(opts: {
  progress: number;
  isManualToggle: boolean;
  edgeEps: number;
}): boolean;
```

Семантика: `!(progress >= 1 - edgeEps || isManualToggle)` — эквивалент
`useToggleVisibility.ts:49`. Граница `>=` включительная: на дне (progress = 1)
и на краю `1 - eps` кнопка видна.

`describe` по функциям, имена GWT (конвенция testing.md). Примерный список:

**`decideScrubBuild`**

- когда не home, scrub-твин не строится (shouldBuild=false, endX=null);
- когда home и homeEndState standard, endX = −0.75 × viewport;
- когда home и homeEndState slim, endX = −(viewport − SLIM_WIDTH);
- когда вьюпорт другой, endX масштабируется;

- когда твина нет (existingProgress=0), prevProgress=0.

prevManual}`:

- `/home`, нет ручного, ручного не было → false (skip, scrub владеет x);
- `/home`, ручное сейчас → true;
- `/home`, ручное было ранее → true;
- не /home → true (анимировать всегда).

**`shouldResyncScrub`**

- `/home`, не manual → true;
- `/home`, manual → false;
- не /home → false.

**`shouldHideToggle`**

- progress=1 → видна (false);
- progress=0.5 → скрыта (true);
- progress=1−eps (граница включительно) → видна (false);
- progress чуть меньше 1−eps → скрыта (true);
- ручной показ (isManualToggle) → видна при любом progress.

## 7. Риски и принятые решения

- **R1 — Рефакторинг хуков меняет поведение.** Митигация: Фаза 0 (базлайн),
  behaviour-preserving рефакторинг, тесты политик; каждую фазу прогоняем
  `npm run test`.
- **R2 — Тавтологические тесты** («политика = копия кода»). Митигация: тесты
  пишутся на языке поведения (GWT-таблицы с числами и сценариями), а не
  пересказом формул.
- **R3 — GSAP в node.** `progress()` синхронен и тикера не требует; риск —
  только если импорт `gsap` зацепит `requestAnimationFrame`. Проверка в
  Фаза 5 до написания тестов; при проблеме — фаза отклоняется (A достаточно).
- **R4 — `EDGE_EPS` дублируется.** Параметр `edgeEps` в `shouldHideToggle` —
  единственный источник остаётся `GsapProvider.tsx:10`; хук подставляет его
  на месте, политика остаётся чистой.
- **R5 — Пропущенный слой — само поведение хука** (подписки/cleanup/конфликт
  scrub vs discrete). Осознанно отложено в Фазу 6 (C): требует смены
  тест-философии и новых зависимостей (D8).
